## Эволюция работы с базой данных и `OpenDB` в `sc-api`

Этот документ описывает текущее состояние доступа к БД в `sc-api`, проблемы подхода с плейсхолдером `{db}` и варианты эволюции в сторону более «нативной» для PostgreSQL архитектуры с учётом режимов изоляции (`sandbox`, `dedicated_schema`, `dedicated_db`).

---

## 1. Текущее состояние

### 1.1. Мастер-БД и `tenant`

- Есть мастер‑БД, в которой живут:
  - таблица `tenant` c полями:
    - `id BIGINT`;
    - `name text`;
    - `subdomain text UNIQUE`;
    - `is_sandbox boolean NOT NULL DEFAULT false`;
    - `isolation isolation_mode NOT NULL DEFAULT 'sandbox'`;
    - `plan text NOT NULL DEFAULT 'sandbox'`;
    - `db_name text NOT NULL`;
    - `created_at timestamptz NOT NULL DEFAULT now()`;
    - `updated_at timestamptz NOT NULL DEFAULT now()` (добавлено миграцией `026_tenant_updated_at.sql`);
  - вспомогательные сущности (`tenant_domain`, view `v_tenant_by_host` и т.д.).
- Мастер‑подключение открывается в `cmd/scapi/internal/server/server.go`:
  - строится DSN вида  
    `host=<DbHost> port=<DbPort> dbname=<MasterName> user=<DbUser> password=<DbPass> sslmode=disable`;
  - создаётся `*sql.DB` (пул соединений) к мастер‑БД;
  - этот же DSN используется для создания `sqlserver.Client`.

### 1.2. `sqlserver.Client` и кэш `tenant → db_name`

- Структура `Client` (`internal/sqlserver/client.go`):
  - держит пул `*sql.DB` (подключение к мастер‑БД);
  - кэш:
    - `dbnames map[string]string` — `tenantId → db_name`;
    - `updated time.Time` — момент последней синхронизации кэша.
- Метод `loadDbNames()`:
  - первый вызов: полный снимок

    ```sql
    SELECT CAST(id AS text) AS tenant_id, db_name, updated_at
    FROM tenant
    ```

    и заполнение `dbnames`;
  - последующие вызовы: инкрементальная загрузка

    ```sql
    SELECT CAST(id AS text) AS tenant_id, db_name, updated_at
    FROM tenant
    WHERE updated_at > $1
    ```

    и «домердживание» обновлённых записей в уже существующую карту;
  - запросы троттлятся через `dbnamesUpdateInterval` (по умолчанию 5 минут), чтобы не спамить мастер‑БД.
- Метод `GetPhysicalDbNames()`:
  - возвращает **уникальный** список физических имён БД (значений `db_name`) из кэша;
  - используется/может использоваться для миграций, health‑check и фоновых задач, чтобы не дублировать операции на одной и той же БД при большом числе тенантов (особенно в песочнице).

### 1.3. `Database` и плейсхолдер `{db}`

- Структура `Database` (`internal/sqlserver/database.go`) содержит:
  - ссылку на `Client`;
  - контекст `ctx`;
  - поле `Name string` — логическое имя базы (для подстановки).
- В запросах используется плейсхолдер `{db}`:
  - перед исполнением каждый метод (`Exec`, `Query`, `QueryRow`, `Select`) вызывает `setDbName()`:

    ```go
    func (d *Database) setDbName(query string) string {
        if d.Name == "" || !strings.Contains(query, "{db}") {
            return query
        }
        return strings.ReplaceAll(query, "{db}", d.Name)
    }
    ```

  - далее выполняется запрос на общем пуле `client.db` (подключение к мастер‑БД).

Фактически текущая модель повторяет подход MSSQL: у нас один пул, а имя БД подставляется в текст запроса через плейсхолдер `{db}`, хотя в PostgreSQL нормальная практика — использовать отдельный DSN/пул на каждую физическую БД.

### 1.4. Миграции `internal/migrate/runner.go`

- Миграционный раннер (`internal/migrate/runner.go`):
  - имеет доступ к `MasterDB *sql.DB`;
  - сам делает запрос:

    ```sql
    SELECT DISTINCT db_name
      FROM tenant
     WHERE db_name IS NOT NULL
     ORDER BY db_name
    ```

  - для каждой БД строит DSN вида  
    `host=<Host> port=<Port> dbname=<db_name> user=<User> password=<Pass> sslmode=<SSLMode>`  
    и открывает отдельное подключение `*sql.DB` для выполнения миграций.

Таким образом, в миграциях уже используется модель «одна физическая БД → отдельный DSN/пул», тогда как в runtime‑клиенте (`sqlserver.Client`/`Database`) пока используется подстановка `{db}`.

---

## 2. Проблемы и ограничения текущего подхода

1. **Непрозрачность для PostgreSQL‑парадигмы**  
   - Подстановка `{db}` в SQL — это «уровень строк», а не уровня соединений/DSN.
   - Невозможно явно выразить, что конкретный запрос идёт в конкретную физическую БД/схему: всё время один и тот же `*sql.DB`.

2. **Ограничения для `dedicated_db`**  
   - Модель `isolation = 'dedicated_db'` предполагает отдельную БД (и, в идеале, отдельный пул соединений) для клиента.
   - С подстановкой `{db}` мы не используем стандартную для PostgreSQL механику `dbname` в DSN и по сути остаёмся на одном пуле.

3. **Мониторинг и тюнинг**  
   - Труднее настраивать лимиты по подключениям на уровне отдельных БД:
     - один пул → общие лимиты;
     - нельзя, например, ограничить особо «тяжёлого» клиента с `dedicated_db`.

4. **Безопасность и читабельность SQL**  
   - Плейсхолдер `{db}` — дополнительный уровень абстракции, который может запутывать чтение запросов и усложнять аудит.
   - Несмотря на то, что подстановка под контролем и не влияет на параметры (`args`), смешение логики выбора базы и текста SQL делает код менее очевидным.

---

## 3. Цели эволюции

1. Максимально использовать **нативную модель PostgreSQL**:
   - отдельный DSN/пул `*sql.DB` для каждой физической БД, когда это оправдано (миграции, `dedicated_db`);
   - для `sandbox`/`dedicated_schema` по возможности работать через общую БД/схему.

2. Сохранить **обратную совместимость** и не ломать текущие вызовы:
   - сигнатура `OpenDB(ctx context.Context, tenantId string) (*Database, error)` должна остаться стабильной;
   - `Database` по-прежнему должен предоставлять `Exec`, `Query`, `QueryRow`, `Select`.

3. Обеспечить **масштабируемость для большого числа песочниц**:
   - избегать слишком большого количества пулов соединений для режимов `sandbox`/`dedicated_schema`;
   - эффективно работать с кэшем `tenant → db_name` и инкрементальной загрузкой.

---

## 4. Варианты эволюции `OpenDB`

### 4.1. Вариант A — зафиксировать текущий подход с `{db}` как v1

**Суть**:
- Оставить одну мастер‑БД и один пул `*sql.DB` для runtime;
- `OpenDB` возвращает `Database` с `Name = db_name`, а `Database` продолжает подставлять `{db}` в SQL.

**Когда это разумно**:
- Нагрузки умеренные, количество физических БД небольшое;
- В приоритете скорость внедрения и простота, а не максимальная чистота архитектуры;
- Режимы `isolation` ещё не активно используются в проде.

**Риски/минусы**:
- Не реализуются преимущества `dedicated_db` на уровне подключения;
- Миграции и runtime используют разные модели (в миграциях уже есть «настоящий» DSN на каждую БД).

### 4.2. Вариант B — карта пулов `map[dbName]*sql.DB` для `dedicated_db`

**Суть**:
- Дополнить `sqlserver.Client`:
  - хранить мастер‑подключение (`masterDB`);
  - кэш `dbnames` (уже есть) +, при необходимости, кэш `isolation` для каждого `tenant`;
  - карту пулов:

    ```go
    type Client struct {
        masterDB *sql.DB

        dbnames   map[string]string       // tenantId -> db_name
        isolation map[string]string       // tenantId -> isolation_mode

        poolsMu   sync.RWMutex
        pools     map[string]*sql.DB      // phys dbName -> *sql.DB
        // ...
    }
    ```

- Реализовать `getDBForName(dbName string) (*sql.DB, error)`:
  - лениво создавать пул `*sql.DB` по DSN с нужным `dbname`;
  - настраивать `SetMaxOpenConns`, `SetMaxIdleConns`, `SetConnMaxLifetime` для таких пулов;
  - кешировать их в `pools`.

- `OpenDB` в зависимости от режима изоляции:
  - `sandbox` / `dedicated_schema` → использовать общий `masterDB` и (при необходимости) `{db}` как префикс/схему;
  - `dedicated_db` → вызывать `getDBForName(db_name)` и создавать `Database`, который:
    - больше **не подставляет** `{db}` (или игнорирует его),
    - работает напрямую с отдельным пулом `*sql.DB`.

**Плюсы**:
- «Правильная» модель для `dedicated_db`: у каждого клиента своя физическая БД и свой пул;
- Проще мониторить и ограничивать потребление ресурсов на уровне отдельных БД;
- Структура кода лучше согласуется с уже существующей логикой в миграциях (`runner.go`).

**Минусы / что нужно продумать**:
- **Количество пулов**:
  - если `dedicated_db` будет много, возможен взрыв числа активных соединений;
  - нужны ограничения по Min/Max коннектам и, возможно, механизм LRU/TTL закрытия неиспользуемых `*sql.DB`.
- **Жизненный цикл**:
  - корректное закрытие всех пулов при остановке сервиса;
  - обработка ошибок при создании пула (БД ещё не создана, временно недоступна и т.п.).

### 4.3. Вариант C — `schema-per-tenant` (для `sandbox`/`dedicated_schema`)

**Суть**:
- Для режимов `sandbox` и `dedicated_schema` использовать одну (или несколько) общих БД, но разные схемы;
- Уйти от подстановки `{db}` в SQL:
  - либо задавать `SET search_path TO <schema>` при входе в контекст `Database`;
  - либо использовать префиксы схемы явно в SQL, но без плейсхолдера.

**Комбинированный подход**:
- `sandbox`, `dedicated_schema` → одна/несколько общих БД, переключение через схемы и `search_path`;
- `dedicated_db` → Вариант B (пул на каждую физическую БД).

**Плюсы**:
- Более естественная для PostgreSQL модель многотенантности;
- Легче управлять общими ресурсами (индексы, расширения и т.д.) в рамках одной физической БД;
- Простая интеграция с уже существующим миграционным раннером (центральная БД + схемы).

**Минусы**:
- Потребуется переработка миграций на схемы (а не только на БД);
- Нужно тщательно продумать, как хранятся и применяются миграции для каждой схемы, чтобы не было конфликтов.

## 5. Предложенный поэтапный план

### Этап 1 — стабилизация текущего решения (выполнено частично)

- Зафиксировать текущий подход с `{db}` как **v1** для PostgreSQL:
  - один пул `*sql.DB` на мастер‑БД в runtime;
  - `Database` подставляет `{db}` в SQL;
  - `OpenDB` получает `db_name` из кэша `tenant → db_name`.
- Оптимизировать работу с `tenant`:
  - уже реализовано поле `updated_at` и инкрементальная загрузка кэша в `sqlserver.Client`;
  - добавлен метод `GetPhysicalDbNames()` для фоновых задач.

### Этап 2 — поддержка `dedicated_db` через `map[dbName]*sql.DB`

1. **Расширить кэш `Client`**:
   - загрузка не только `db_name`, но и `isolation` (`isolation_mode`) в отдельную структуру:

     ```sql
     SELECT CAST(id AS text) AS tenant_id, db_name, isolation, updated_at
       FROM tenant
     ```

   - мапа вида `map[string]TenantMeta`, где `TenantMeta` содержит `DbName`, `Isolation`, `IsSandbox`.

2. **Реализовать карту пулов**:
   - добавить в `Client` поля:

     ```go
     poolsMu sync.RWMutex
     pools   map[string]*sql.DB  // dbName -> *sql.DB for dedicated_db
     ```

   - реализовать `getDBForName(dbName string) (*sql.DB, error)` с ленивым созданием пула и базовыми лимитами.

3. **Изменить `OpenDB`**:
   - по `tenantId` получать `TenantMeta` (из кэша);
   - если `TenantMeta.Isolation == "dedicated_db"`:
     - использовать `getDBForName(meta.DbName)`,
     - создавать `Database`, который не использует `{db}` (или игнорирует его);
   - иначе (sandbox/dedicated_schema):
     - оставлять нынешнюю логику: общий пул + при необходимости `{db}` (до момента, когда перейдём на схемы).

4. **Интеграция с миграциями**:
   - опционально унифицировать открытие БД в миграционном раннере и в `sqlserver.Client`, чтобы использовать общие настройки (retry‑логика, лимиты, трейсинг).

### Этап 3 — схемы для `sandbox`/`dedicated_schema` (опционально, последующим этапом)

- Спроектировать, как именно будет выглядеть `schema-per-tenant`:
  - соглашение об именовании схем (`tenant_<id>` или по `subdomain`);
  - миграции по схемам: либо один набор SQL с параметризованным именем схемы, либо отдельные миграции на схему;
  - переключение `search_path` в `Database` в зависимости от `tenantId`.
- Постепенно уводить запросы от `{db}`:
  - сначала для песочниц и `dedicated_schema`;
  - затем, при необходимости, полностью убрать плейсхолдер `{db}` из SQL.

---

## 6. Резюме

- **Сейчас**: стабильное решение с одним пулом `*sql.DB` и подстановкой `{db}` в SQL, кэш `tenant → db_name` с инкрементальной загрузкой по `updated_at`.  
- **Ближайшая эволюция**: добавить поддержку `dedicated_db` через карту пулов `map[dbName]*sql.DB`, сохранив текущий интерфейс `OpenDB` и не ломая режимы `sandbox`/`dedicated_schema`.  
- **Дальнейшая перспектива**: рассмотреть переход на `schema-per-tenant` для песочниц и `dedicated_schema`, чтобы ещё сильнее приблизиться к нативной PostgreSQL‑модели многотенантности и в итоге избавиться от плейсхолдера `{db}`.
