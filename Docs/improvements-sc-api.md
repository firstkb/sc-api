## Улучшения архитектуры `sc-api`

Этот документ фиксирует предложения по развитию архитектуры и отмечает, какие из них будут затронуты в рамках миграции на PostgreSQL.

### 1. Слоистая архитектура и DDD‑подход

- **1.1. Ввести явные интерфейсы репозиториев (Repository interfaces)**  
  - Определить интерфейсы репозиториев в application/domain‑слое (например, `PingRepository`, `PageRepository`), а не полагаться на конкретные реализации `sqlserver.Repository`.  
  - Выигрыш: упрощённая подмена реализаций (PostgreSQL, mock), лучшая тестируемость, сниженная связанность.

- **1.2. Отделить доменную модель от DTO и инфраструктуры**  
  - Создать отдельные доменные структуры (например, `Page`) и отделить их от структур, которые напрямую маппятся на таблицы (`ExtDBpg`).  
  - Репозитории должны возвращать доменные сущности, а не «сырые» структуры БД.  
  - В будущем можно добавить фабрики/mapper’ы между доменной моделью и слоем хранения.

- **1.3. Разделить ответственность между слоями**  
  - HTTP‑слой (`server`) не должен напрямую знать о деталях подключения к БД; инициализацию клиента БД стоит вынести в композиционный/инфраструктурный слой и передавать в `Server` уже готовые сервисы.  
  - Application‑сервисы должны инкапсулировать бизнес‑операции и использовать интерфейсы репозиториев, а не конкретные типы `sqlserver`.

### 2. Слой работы с БД и миграция на PostgreSQL

- **2.1. Абстракция клиента БД**  
  - Ввести интерфейс, описывающий минимальный контракт клиента БД (открытие контекста БД по `client_id`, исполнение запросов, базовая трассировка).  
  - Текущий `sqlserver.Client` реализует этот контракт; новая реализация для PostgreSQL должна повторять поведение (включая мультитенантность через таблицу `client_config` или аналог).

- **2.2. Замена MSSQL‑специфичных конструкций на совместимые с PostgreSQL**  
  - Переписать SQL‑запросы, используя:  
    - `LIMIT 1` вместо `TOP(1)`;  
    - `COALESCE(col, '')` вместо `ISNULL(col, '')`;  
    - плейсхолдеры `$1, $2, ...` (или именованные) вместо `@p1`;  
    - явную схему/имя БД в стиле PostgreSQL (возможно, с использованием схем вместо отдельных БД).  
  - Обновить код, который полагается на тип `rowversion`, на использование подходящего типа/механизма в PostgreSQL (например, `bytea` + триггеры, `xmin`, timestamp‑версирование).

- **2.3. Централизация и конфигурируемость подключений**  
  - Вынести параметры подключения к БД (host, port, db, user, password, SSL) в конфигурацию и `.env`, явно задокументировать их.  
  - Обеспечить единообразную инициализацию пула соединений (например, через `database/sql` + драйвер PostgreSQL) с настройкой лимитов соединений, timeout’ов и т.п.

### 3. Обработка ошибок, логирование и наблюдаемость

- **3.1. Стандартизировать коды и категории ошибок**  
  - Определить перечень «кодов операций» и «типов ошибок» (валидация, доступ, внутренняя ошибка, внешние сервисы).  
  - Убедиться, что `wrapErr` и `apperr` последовательно используют эти коды и корректно маппят их на HTTP‑статусы.

- **3.2. Улучшить retry‑логику**  
  - Реализовать в `runWithRetry` реальные правила повторов для транзиентных ошибок (timeout, deadlock, сетевые сбои) с ограничением по числу попыток и backoff.  
  - В случае PostgreSQL использовать узнаваемые по коду/классу SQLSTATE ошибки как критерий для retry.

- **3.3. Добавить метрики и (опционально) трейсинг**  
  - Ввести базовые метрики:
    - длительность HTTP‑запросов по эндпоинтам;
    - длительность и количество SQL‑запросов, количество ошибок;
    - пул соединений с БД (взято/свободно).  
  - При необходимости интегрировать OpenTelemetry/Prometheus.

### 4. Тестируемость и качество кода

- **4.1. Юнит‑тесты для репозиториев и сервисов**  
  - Ввести интерфейсы для зависимостей (клиент БД, репозитории), чтобы можно было подменять их в тестах мок‑реализациями.  
  - Написать юнит‑тесты для `PingService`, репозиториев и основных веток обработки ошибок.

- **4.2. Интеграционные тесты с PostgreSQL**  
  - Настроить запуск тестового PostgreSQL (например, в Docker) и добавить интеграционные тесты для критичных сценариев:  
    - выбор имени БД по `client_id`;  
    - выполнение типовых SQL‑операций (чтение/запись) для «тенантской» БД.  

- **4.3. Линтеры и форматирование**  
  - Подключить `golangci-lint` (или аналог) с базовым набором правил (устранение неиспользуемого кода, упрощение конструкций, проверка ошибок и т.п.).  
  - Обеспечить единый стиль форматирования (`go fmt`) и, при необходимости, добавить pre‑commit‑хуки.

### 5. Улучшения конфигурации и `.env`

- **5.1. Явная документация по конфигурации**  
  - Описать в отдельном документе (`Docs/env.md`) все поддерживаемые переменные окружения и их связь с конфиг‑ключами.  
  - Добавить `.env.example`, отражающий минимально необходимый набор переменных для локального запуска.

- **5.2. Консистентность имён переменных**  
  - Привести имена переменных окружения к единому стилю (`SCAPI_DB_HOST`, `SCAPI_DB_PORT`, `SCAPI_DB_NAME`, и т.д.), учитывая уже используемую схему с префиксом `SCAPI_`.  
  - Обновить существующую конфигурацию так, чтобы все ключевые настройки могли быть заданы через `.env`/ENV без изменения бинарника.

### 6. Приоритезация (ближайшие шаги)

- **В рамках миграции на PostgreSQL** в первую очередь будут затронуты:  
  - абстракция клиента БД и перенос на PostgreSQL (п.2.1–2.3);  
  - частичное отделение persistence‑слоя от HTTP‑слоя (инициализация БД и репозиториев);  
  - документирование конфигурации и `.env` (п.5.1–5.2);  
  - добавление первых юнит/интеграционных тестов для слоя БД (п.4.1–4.2).

- **Следующие итерации** могут быть посвящены более глубокому внедрению DDD, расширению доменной модели, введению продвинутых метрик/трейсинга и доработке retry‑механизмов.
